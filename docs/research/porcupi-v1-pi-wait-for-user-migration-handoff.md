# PorcuPi v1: minimal `pi-wait-for-user` migration handoff

## Status and fixed reference

This is the decision-complete handoff for PorcuPi [#10](https://github.com/taylorrowser/PorcuPi/issues/10). It applies the reduced scope from [#11](https://github.com/taylorrowser/PorcuPi/issues/11#issuecomment-5106527557), the composition/lifecycle contract from [#7](https://github.com/taylorrowser/PorcuPi/issues/7#issuecomment-5106583361), and the accepted command surface from [#9](https://github.com/taylorrowser/PorcuPi/issues/9#issuecomment-5108738122).

The only reference implementation for this handoff is [`taylorrowser/pi-wait-for-user@1a987bca79a4f9475dd2037c18b2d6d7b7f68f25`](https://github.com/taylorrowser/pi-wait-for-user/tree/1a987bca79a4f9475dd2037c18b2d6d7b7f68f25). PorcuPi should move or narrowly adapt its tested local behavior; it should not reproduce the reference distribution architecture.

## Boundary

After migration:

- **`pi-wait-for-user` remains a Git Source Repository.** It owns the Patch files under `patches/active/`, the independently installable Question Tool Pi package under `packages/question-tool/`, tests/documentation for that content, and optional narrow `porcupi.json` display/exact-Pi-Base metadata.
- **PorcuPi owns general machinery.** It owns the exact Pi Base, Patch selection, fixed local build recipe, composition receipts, immutable publication, active/previous selection, launch, leases, rollback, optional `pi` command ownership, verification, and owned cleanup.
- **Pi owns non-Patch resources.** The Question Tool remains a normal Pi package resource rather than becoming a privileged build input or a PorcuPi dependency. `pi-wait-for-user` may document that users should select it, but v1 adds no dependency graph or automatic coupling.
- **Existing published releases remain immutable historical artifacts.** Existing users leave the old manager by running its own uninstall, then install PorcuPi and select the Git source. PorcuPi does not adopt legacy manager state or payloads.

## Explicitly left behind

Do **not** move these reference components into PorcuPi v1:

- `scripts/lib/release-metadata.mjs`, `scripts/release-metadata.mjs`, `scripts/bootstrap.sh`, release trust/Channel/Manifest schemas, delegated keys, signatures, replay checkpoints, release promotion, checksums, provenance/attestations, and release bundle machinery;
- `scripts/lib/managed-update.mjs`, update routing, startup refresh, Patch Lag, online discovery, diagnostics for network update stages, Update Holds, and background notices;
- Manager Release/Downstream Release pair compatibility, versioned Manager payloads, stable dispatcher extraction from a Manager Release, and paired artifact archives;
- arbitrary rollback targets, pin/unpin/prune commands, arbitrary retained pairs, and release IDs as a user-facing retention mechanism;
- Legacy Downstream Installation discovery/adoption and migration state;
- Windows bootstrap, launchers, process probing, archive behavior, and deferred executable-lock cleanup;
- release candidate reports/gates as local activation authorities, publisher manifests beyond #9's narrow optional Patch display/exact-base metadata, Question Tool special bundling, session compatibility publication, and Stock Pi execution wrappers;
- per-Artifact projection/receipt/update machinery, generalized build adapters, dependency solving, hooks, Patch scripts, force activation, and every other feature removed by #11.

## Ordered, deletion-oriented migration

1. **Freeze the reference.** Record `1a987bca…` and Pi Base `20be4b18…` in PorcuPi fixtures. Add an integration fixture that points at the exact `pi-wait-for-user` source commit and expects all 20 `patches/active/*.patch` files in canonical order.
2. **Port tests before machinery.** Copy and reshape the reference Patch-workspace tests for exact-base rejection, all-series preflight, deterministic application, and preparation. Copy lifecycle acceptance cases only for atomic active/previous selection, fail-closed launch, local verify, default rollback, lifecycle serialization, leases, receipt-scoped cleanup, optional `pi` collision safety, and uninstall preservation.
3. **Implement Source/Patch inputs.** Add exact Git source resolution, recursive regular-file discovery, optional narrow metadata, commit/digest capture, saved selection intent, and canonical cross-source order. Route non-Patch selections into Pi package configuration only.
4. **Move the fixed build recipe.** Adapt `readLock`/`verifySource`, `preflightPatches`, `applyPatches`, and `prepare`; then run the exact install/hydrate/offline-build/conformance/version/isolated-smoke sequence. Produce a staged Composition receipt and immutable payload. Delete any provisional alternate build path as soon as this vertical slice passes.
5. **Collapse the lifecycle.** Adapt atomic writes, the lifecycle lock, stages, receipt comparison, immutable publication, cheap/full verification, launch, Composition leases, tombstone cleanup, and active/previous switch. Implement one Composition type directly; do not first port Pair/Manager abstractions and simplify later.
6. **Publish the accepted CLI.** Wire the #9 `add`, `manage`, `apply`, `verify`, `rollback`, `pi enable|disable`, launch, and uninstall flows to these seams. `apply` is the only Patch build/activation trigger; selection save alone never mutates Activation.
7. **Prove the real handoff.** On macOS and Linux, select the exact `pi-wait-for-user` source, compose its complete 20-Patch series on the pinned Pi Base, install/select its Question Tool through Pi, launch, verify, fail an apply without switching, successfully switch, rollback, exercise a live lease, disable/re-enable `pi`, and uninstall while hashing shared Pi data before/after.
8. **Cut the first accepted PorcuPi release.** The release must pass the evidence below from a clean machine with and without Stock Pi and with foreign launcher collisions. Document old-manager exit as: run the old manager's uninstall, then install PorcuPi and add the Git source. There is no automatic legacy adoption.
9. **Reduce `pi-wait-for-user` to source content.** Add the narrow root `porcupi.json` metadata when its schema exists; keep `patches/active/`, `packages/question-tool/`, their content tests/docs, and immutable historical tags/releases. Remove current-branch claims that this repo installs, activates, updates, or owns `pi`.
10. **Delete duplicated machinery.** In one cleanup change, remove the source-build installer/launcher, managed installer/manager/dispatcher/runtime/update libraries, release/signing/channel/provenance tooling, manager lifecycle tests, Windows manager machinery, release candidate/gate projections, and executable upstream lock. Keep only content-facing tests and any minimal repository tooling needed to validate the Patch files and Question Tool as source artifacts.

### Exact deletion gate

Step 10 may begin only after all of the following are true:

1. a released PorcuPi version can consume `pi-wait-for-user` at an exact Git commit without copied Patch files;
2. that release passes the full macOS/Linux real-source walkthrough in step 7;
3. PorcuPi's tests independently cover the retained failure/crash/ownership boundaries below; and
4. `pi-wait-for-user`'s default branch points users to PorcuPi and contains any accepted narrow Patch compatibility metadata.

At that point the old implementation is no longer a fallback or second authority. Historical tags/releases remain available so an existing installation can run its own uninstall, but no manager code remains live on the source repository's default branch.

## Acceptance evidence

PorcuPi's implementation tickets must preserve observable behavior, not private helper names:

- malformed/wrong Pi Base fails before dependency installation;
- recursive discovery accepts only regular `*.patch` files and canonical ordering is stable across Sources;
- wrong Source commit or Patch digest fails before preflight/build;
- if any Patch in the sequential preflight fails, the build checkout and Activation remain unchanged;
- zero Patches builds the exact Pi Base;
- the fixed command sequence is invoked in order and each failure removes only owner-proven staging;
- a receipt binds exact base, ordered Patch identities, recipe/platform, executable, and complete payload;
- interruption before/after publication and Activation rename exposes only old or complete new state;
- launch fails closed for malformed state, receipt mismatch, platform mismatch, or changed executable;
- full verify detects payload changes and reruns version/smoke/conformance;
- rollback has only previous/no-target paths, performs no network/build, and swaps committed Patch selections;
- lifecycle mutation serializes while existing launched Pi processes continue under leases;
- cleanup never removes active/previous/live-leased or foreign content and converges later;
- `pi` enable/disable refuses collisions and never modifies Stock Pi;
- uninstall preflights ownership and preserves Pi packages, settings, credentials, sessions, trust, and project data;
- all retained behavior passes on macOS and Linux, with no Windows acceptance requirement.

As source evidence, the pinned reference was archived and exercised locally with Node's test runner. `test/patch-workspace.test.mjs` plus `test/install.test.mjs` passed **9/9**. A retained-lifecycle subset selected by test name from `test/managed-runtime.test.mjs` passed **10/10**, covering atomic Activation, switch interruption, fail-closed launch, full verification, rollback/no-target/interruption, lifecycle serialization, lease-deferred owned cleanup, and uninstall preservation. The relevant source tests are [`patch-workspace.test.mjs`](https://github.com/taylorrowser/pi-wait-for-user/blob/1a987bca79a4f9475dd2037c18b2d6d7b7f68f25/test/patch-workspace.test.mjs#L81-L135) and [`managed-runtime.test.mjs`](https://github.com/taylorrowser/pi-wait-for-user/blob/1a987bca79a4f9475dd2037c18b2d6d7b7f68f25/test/managed-runtime.test.mjs#L349-L899).
